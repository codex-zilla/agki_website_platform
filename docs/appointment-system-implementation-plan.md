# AGKI Appointment System — Implementation Plan & Tracker

**Design reference:** [appointment-system-redesign.md](appointment-system-redesign.md)
**Covers:** `appointments/` (public booking) and `doctorDashboard/` (staff console)
**Status legend:** 🔲 Not started · 🟡 In progress · ✅ Done · ⛔ Blocked · ⏭️ Skipped (see notes)

How to use this doc: update the **Status** cell as work happens, and always leave a line in **Notes / Remarks** when a step is closed — even a one-liner ("done, no issues"). A blank notes cell on a ✅ step is a smell; a step marked ⛔ must have a note explaining what's blocking it. Treat this file as the log a reviewer (or future-you) reads to understand *why* something was done a certain way, not just *that* it was done.

**This project is different from the CMS one in a way that shapes every phase below:** the CMS built something new alongside a working site. This one touches a system that is **live, holds patient data, and is currently exploitable by anonymous visitors**. Phase 1 exists to close those holes before anything else, and it deliberately depends on nothing else in this plan.

### Running the pre-flight checks

```bash
# 1. Snapshot before touching anything (run on the host, before 9.4)
cp db.sqlite3 "backups/db.sqlite3.$(date +%Y%m%d-%H%M%S).pre-phase2"
tar czf "backups/media.$(date +%Y%m%d-%H%M%S).tar.gz" media/

# 2. Audit. Read-only — safe to run directly against production.
python manage.py audit_appointment_data              # human report
python manage.py audit_appointment_data --strict     # exit 1 if a migration would fail
python manage.py audit_appointment_data --json       # for a ticket or a diff between runs
```

Re-run the audit after resolving anything it reports, and again immediately before 9.4. `--strict` is the form to use in a deploy script: BLOCKER means a Phase 2 migration will fail on this data, REVIEW means a person has to decide something first, INFO is scope sizing only.

### 3.7 Why delivery runs from cron, and what else was considered

You asked about a service worker, a cron job "or something similar". The short answer is cron, and the reasoning is worth writing down because the alternatives fail for different reasons.

| Approach                                     | Verdict                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Send inline, in the request**        | Rejected. It couples two unrelated things: a mail server having a slow afternoon makes booking*feel* broken, and a mail server that is down makes booking *be* broken — for a message that is not part of booking. It also leaves a failed send nowhere to go: no retry, no record, nothing to tell an administrator afterwards.                                                                                                                               |
| **Service worker**                     | Not applicable, and worth being precise about: a service worker runs in the**visitor's browser**. It can show a Web Push notification to somebody who has visited the site and granted permission; it cannot send email or SMS, and it does not run when nobody is visiting. It would be a reasonable *addition* later if AGKI wants doctors to get browser alerts on top of email — a separate feature, needing VAPID keys and a push subscription store. |
| **Celery / RQ / a task queue**         | Rejected on this host. Both need a broker (Redis, RabbitMQ) and a long-running worker process. Shared cPanel hosting provides neither.                                                                                                                                                                                                                                                                                                                              |
| **A background thread in the request** | Rejected. Passenger starts and kills application processes as it pleases, so a thread can be killed mid-send with the row still marked pending and nobody the wiser.                                                                                                                                                                                                                                                                                                |
| **Cron + a database outbox** ✅        | What shipped. Cron is the one scheduler this host actually offers, Phase 6 needs it anyway for expiry, and the outbox table was already in the design (§9.1) for auditing — making it the queue as well costs one status column and gives retries, a record of what was said, and a place for an administrator to look.                                                                                                                                           |

**The one failure mode, and it is silent:** with `NOTIFICATIONS_DELIVERY=queued` and no cron entry, messages queue forever and nobody is told anything. Same class of failure as the expiry cron in 6.4, and it needs the same treatment — watch a real run, do not just add the entry. In development the default is `immediate`, so a developer sees messages in the console without running cron.

```
# cPanel → Cron Jobs. Every minute; the command is bounded (--limit) and
# safe to overlap with itself.
* * * * * cd /home/<user>/<app> && /home/<user>/virtualenv/<app>/3.12/bin/python manage.py send_pending_notifications >> /home/<user>/logs/notifications.log 2>&1
```

### 4.1a A ninth notification event, not in the design's eight

Design §9.1 lists eight events. ### 10.y The gate found a live authentication bug, outside this phase

**The public signup form's email verification did not gate anything.** Writing the gate test surfaced it on its first assertion, and it is worth stating plainly because it was in production behaviour, not in Phase 10's changes:

`CustomUser.objects.create_user()` fires the signal in `useraccount.signals`, which holds a public signup by writing `is_active=False` **to the row**. `signup` then set `first_name`, `phone`, `role` and so on on the same in-memory instance and called a plain `.save()` — writing `is_active=True` back over it, because the signal updated the row and not the object. So the account came out **active**: the one-time code was generated, emailed, and gated nothing. Anyone could register and sign in without ever opening the message.

**Nothing in the suite could see it.** The existing signal test calls `create_user` directly and stops one line before the call that undid its work, and every other test that needed a user made one directly too. It took a test that went through the actual form.

**Fixed** by narrowing the save to `update_fields`, with four regression tests (`SignupVerificationGateTests`) covering both directions — an unverified registrant cannot authenticate, and one who uses the code can — mutation-checked by restoring the plain `.save()` and confirming three tests fail.

**This is outside 10.5 and outside Phase 10.** It is recorded here because Phase 10 is what made it matter: decision F grants approval at registration, so controlling the email address became the *only* thing a registrant has to prove (design §4.5) — and this was the line that meant they did not have to prove even that.

⚠️ **It also falsified two sentences written earlier in this phase.** 10.1's note says a form registration lands "approved **and inactive** until the address is verified", and design §4.5 says a form registration "still has to clear an emailed one-time code". Both described the signal's intent and were true of `create_user`; neither was true of the form. They are true now, because of this fix — not because they were right when written.

**Ordering:** 10.1 and 10.2 ship together or not at all. The new default without the backfill leaves every existing doctor exactly as locked out as they are today, which is the failure 1.10 already warned about, arriving a second time under a decision meant to prevent it.

## Open risks / carry-forward notes

- ~~**Four tests pass or fail depending on the day of the week and the time of day.**~~ **Closed on 2026-08-29** — all four fixed and mutation-checked, and the suite swept for others of the same shape (10.x). The suite is green on a day it used to be red, which is the only form of "fixed" that means anything here.
- ⚠️ **Anyone who can receive email can register as a publicly bookable doctor** (decision F, design §4.5). This is the largest open risk in the project, and it is *accepted deliberately* rather than overlooked: self-registration ships before any credential check exists, so control of an email address is the only thing between a stranger and a doctor listing on a medical booking platform. The mitigation is reactive — an administrator withdraws `is_approved` once somebody complains — and it is only a real mitigation after 10.3, which makes that also remove the public listing. **Design the verification method (§4.5) before this platform is promoted to patients**, not after.
