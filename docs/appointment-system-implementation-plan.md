# AGKI Appointment System — Implementation Plan & Tracker

**Design reference:** [appointment-system-redesign.md](appointment-system-redesign.md)
**Covers:** `appointments/` (public booking) and `doctorDashboard/` (staff console)
**Status legend:** 🔲 Not started · 🟡 In progress · ✅ Done · ⛔ Blocked · ⏭️ Skipped (see notes)

How to use this doc: update the **Status** cell as work happens, and always leave a line in **Notes / Remarks** when a step is closed — even a one-liner ("done, no issues"). A blank notes cell on a ✅ step is a smell; a step marked ⛔ must have a note explaining what's blocking it. Treat this file as the log a reviewer (or future-you) reads to understand *why* something was done a certain way, not just *that* it was done.

**This project is different from the CMS one in a way that shapes every phase below:** the CMS built something new alongside a working site. This one touches a system that is **live, holds patient data, and is currently exploitable by anonymous visitors**. Phase 1 exists to close those holes before anything else, and it deliberately depends on nothing else in this plan.

## Phase 1 — Security hardening (ships first, alone, depends on nothing)

Design §11 step 0. Every item here is currently exploitable by an **anonymous** visitor, verified by reproduction against a throwaway database. None of it needs the state machine, the notification layer, or a design sign-off. **Do not let this phase wait on the rest of the plan.**

| 1.5  | `ecommerce_items` → `is_superuser`-only, read-only | ✅ | `@superuser_required`, stricter than any role: `role=admin` and `role=doctor` both get 403. | 1.6  | Fix the IDOR on patient records | ✅ | [appointments/access.py](../appointments/access.py). Both patient-record URLs key off `bookingID`; the integer routes are gone rather than redirected, since incrementing that integer *was* the vulnerability. **One thing the design didn't state and that turned out to matter:** `booking_success_page` keyed off the same integer, so letting it grant the marker would have re-opened the hole through the back door. The marker is granted in `booking_form`, to the person who just filled the form in, and the success page then *checks* it like any other page. An unknown booking ID and a forbidden one produce byte-identical responses, so the page can't be used as an oracle. Markers are `django.core.signing`-signed and expire after 7 days — a candidate to move onto `AppointmentSettings` at 2.1. |
| 1.7  | `booking_id_lookup` requires a second verification field | ✅ | One field accepting **either** phone or date of birth: asking a walk-in patient to remember which of the two the form wants is friction with no security value. Phone matching compares the last nine digits, so `+255 712 345 678` and `0712345678` both work; DOB accepts four common formats. One generic error for every failure mode. **Scope note — this also required deleting the page's JavaScript**, which wasn't listed as Phase 1 work but made 1.7 impossible: the submit handler called `preventDefault()` unconditionally and never submitted, and the input rewrote whatever was typed into MediBook's `MB-` format, so no `AGKI-` booking ID could ever be entered (design finding appointments #2). The form is now a plain HTML POST. |
| 1.8  | Rate-limit the lookup endpoint | ✅ | [appointments/ratelimit.py](../appointments/ratelimit.py) — hand-rolled fixed window, 5 attempts / 10 minutes per IP, HTTP 429, per decision 0.5. `REMOTE_ADDR` only: `X-Forwarded-For` is attacker-controlled with no trusted proxy configured, so honouring it would let anyone rotate their limit away with a header — there is a test for exactly that. **The `CACHES` change is not what 0.5 described, and the difference matters.** Pointing the *default* cache at the database broke `HomePageCacheTests`, correctly: it turned the homepage's zero-query cache hit into a query. So there are two caches now — `default` stays in-process for rendered content, and a separate database-backed `ratelimit` alias holds the counters every Passenger worker has to agree on. |
| 1.9  | Fix `post_login_redirect` for `role=admin` | ✅ | `role in (doctor, admin)` → dashboard, before the `is_staff` check. `PostLoginRedirectTests` gains a `lab administrator` row modelled on the real `kulwa_cherehani` (role=admin, is_staff, not superuser). **She will land on an empty dashboard** until 5.10 widens the querysets — the views still filter to `slot__user=request.user`. Better than never reaching the console at all, but not finished, and 5.10 is where it finishes. |
| 1.10 | Enforce `is_approved` at login | ✅ | Enforced in `EmailBackend.user_can_authenticate`, **not** in `signin()` as the design's letter said. In the view it would have left every other entry point ungated, and one of those mattered: allauth logs users in through its own backend, so "Sign in with Google" would have walked straight around the gate. An `ACCOUNT_ADAPTER.pre_login` hook covers that path too. Three consequences worth knowing: (a) enforcing it in the backend means `get_user` refuses as well, so un-approving an account ends its **existing session**, not just its next login — which is what an admin clicking the toggle expects; (b) `createsuperuser` would otherwise produce an account that can't use the site's own login form, so new superusers are auto-approved on creation; (c) **`/admin/login/` remains reachable** with a username, because it authenticates through `ModelBackend`. That is the deliberate recovery path if this locks everyone out, and it is a real gap for `is_staff` accounts — accepted because admin access is already governed by `is_staff` plus model permissions. **Ship prerequisite: 6 of 10 local accounts, both superusers among them, have `is_approved=False`.** Run the 0.3 audit against prod and approve that list first. |
| 1.11 | Tests for every item above | ✅ | **48 new tests, 145 total**, with the CMS's 80 intact: [doctorDashboard/tests.py](../doctorDashboard/tests.py) 16, [appointments/tests.py](../appointments/tests.py) +23, [useraccount/tests.py](../useraccount/tests.py) +9. The access tests enumerate `doctorDashboard.urls` rather than a hand-written list, and a route capturing an unrecognised parameter raises `KeyError` and fails every test in the module — so adding a view without deciding who may reach it is not a reachable state. **Mutation-checked:** all twelve fixes were reverted one at a time and the suite re-run; every one was caught, by the tests that should have caught it. |

**Phase gate:** ✅ **met.** An anonymous visitor is refused by every dashboard route, no destructive endpoint responds to any method, and patient PII is unreadable without proving a claim to it — each verified by a test that has been shown to fail when its fix is removed, not by inspection.

1. `python manage.py audit_appointment_data` — the `login_lockout_risk` rows are the accounts 1.10 locks out. Approve them **first** (`/admin/` → Users → Approved).
2. `python manage.py createcachetable` — one-off, per environment. Without it the lookup endpoint raises instead of rate-limiting. Already run on local dev.
3. Sanity-check one real sign-in per role, the lab administrator especially (9.9).

**Deliberately left to later phases so this ships alone:** `role=admin` still sees only their own slots (5.10); `/doctorDashboard/base/` and `/schedule/` still exist, now behind auth (5.7, 5.9); the orphan `appointment_details.html` is still there (5.8); the lookup page still promises "email or SMS" (3.6) and still carries MediBook branding (7.3).

## Open risks / carry-forward notes

- ~~**The branch question (0.1) blocks everything except Phase 1.**~~ **Closed** — the CMS work is already merged; `main` and both feature branches are the same commit. See 0.1.
- **Two Phase 2 migrations can fail on real data** (duplicate slots; multiple appointments per slot). Both are *confirmed possible* in the current code, so prod may already violate them. 0.3's audit is not optional. **Local dev result: one duplicate slot pair (ids 16/17), no multi-appointment slots — but local holds zero appointments, so that second result proves nothing about prod.**
- **`is_approved` enforcement (1.10) can lock out existing staff** the moment it ships. **Local: 6 of 10 active accounts have `is_approved=False`, including both superusers and three doctors** — so on this data 1.10 locks out almost everyone until they are approved. `audit_appointment_data` names them (`login_lockout_risk`); run it on prod and approve the list *before* shipping 1.10, not after.
- **Expiry silently does nothing without cron** (0.6, 6.4, 9.5). Verify a real run, don't just add the entry.
- ~~**Per-process cache weakens rate limiting** (0.5).~~ **Decided** — moving to `DatabaseCache` alongside the hand-rolled limiter, so the limit is shared across Passenger workers. Ships with 1.8. Note the change is not free of its own risk: every rate-limit check becomes a DB write, so the cache table needs `clearsessions`-style culling (`MAX_ENTRIES` is enough here) rather than growing unbounded.
- **Still open from the design:** whether anyone bookable is *not* a doctor (proceeding with "Doctor" as the public term). Only revisit if nurses or technicians become directly bookable.
- **`useraccount` debris** noted during the CMS cleanup and still present: `/useraccount/` serves a 13-line developer scratch page ("QR Code Generator" / "McColn Basement"), and `useraccount/urls.py` registers `name='profile'` twice so one of the two views is unreachable by name. Neither blocks this project; both are adjacent enough to fold in cheaply.
