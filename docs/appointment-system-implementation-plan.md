# AGKI Appointment System — Implementation Plan & Tracker

**Design reference:** [appointment-system-redesign.md](appointment-system-redesign.md)
**Covers:** `appointments/` (public booking) and `doctorDashboard/` (staff console)
**Status legend:** 🔲 Not started · 🟡 In progress · ✅ Done · ⛔ Blocked · ⏭️ Skipped (see notes)

How to use this doc: update the **Status** cell as work happens, and always leave a line in **Notes / Remarks** when a step is closed — even a one-liner ("done, no issues"). A blank notes cell on a ✅ step is a smell; a step marked ⛔ must have a note explaining what's blocking it. Treat this file as the log a reviewer (or future-you) reads to understand *why* something was done a certain way, not just *that* it was done.

**This project is different from the CMS one in a way that shapes every phase below:** the CMS built something new alongside a working site. This one touches a system that is **live, holds patient data, and is currently exploitable by anonymous visitors**. Phase 1 exists to close those holes before anything else, and it deliberately depends on nothing else in this plan.

## Phase 1 — Security hardening (ships first, alone, depends on nothing)

Design §11 step 0. Every item here is currently exploitable by an **anonymous** visitor, verified by reproduction against a throwaway database. None of it needs the state machine, the notification layer, or a design sign-off. **Do not let this phase wait on the rest of the plan.**

| 1.6  | Fix the IDOR on patient records | ✅ | [appointments/access.py](../appointments/access.py). Both patient-record URLs key off `bookingID`; the integer routes are gone rather than redirected, since incrementing that integer *was* the vulnerability. **One thing the design didn't state and that turned out to matter:** `booking_success_page` keyed off the same integer, so letting it grant the marker would have re-opened the hole through the back door. | 1.7  | `booking_id_lookup` requires a second verification field | ✅ | One field accepting **either** phone or date of birth: asking a walk-in patient to remember which of the two the form wants is friction with no security value. Phone matching compares the last nine digits, so `+255 712 345 678` and `0712345678` both work; DOB accepts four common formats. One generic error for every failure mode. **Scope note — this also required deleting the page's JavaScript**, which wasn't listed as Phase 1 work but made 1.7 impossible: the submit handler called `preventDefault()` unconditionally and never submitted, and the input rewrote whatever was typed into MediBook's `MB-` format, so no `AGKI-` booking ID could ever be entered (design finding appointments #2). The form is now a plain HTML POST. |
| 1.8  | Rate-limit the lookup endpoint | ✅ | [appointments/ratelimit.py](../appointments/ratelimit.py) — hand-rolled fixed window, 5 attempts / 10 minutes per IP, HTTP 429, per decision 0.5. `REMOTE_ADDR` only: `X-Forwarded-For` is attacker-controlled with no trusted proxy configured, so honouring it would let anyone rotate their limit away with a header — there is a test for exactly that. **The `CACHES` change is not what 0.5 described, and the difference matters.** Pointing the *default* cache at the database broke `HomePageCacheTests`, correctly: it turned the homepage's zero-query cache hit into a query. So there are two caches now — `default` stays in-process for rendered content, and a separate database-backed `ratelimit` alias holds the counters every Passenger worker has to agree on. |
| 1.9  | Fix `post_login_redirect` for `role=admin` | ✅ | `role in (doctor, admin)` → dashboard, before the `is_staff` check. `PostLoginRedirectTests` gains a `lab administrator` row modelled on the real `kulwa_cherehani` (role=admin, is_staff, not superuser). **She will land on an empty dashboard** until 5.10 widens the querysets — the views still filter to `slot__user=request.user`. Better than never reaching the console at all, but not finished, and 5.10 is where it finishes. |
| 1.10 | Enforce `is_approved` at login | ✅ | Enforced in `EmailBackend.user_can_authenticate`, **not** in `signin()` as the design's letter said. In the view it would have left every other entry point ungated, and one of those mattered: allauth logs users in through its own backend, so "Sign in with Google" would have walked straight around the gate. An `ACCOUNT_ADAPTER.pre_login` hook covers that path too. Three consequences worth knowing: (a) enforcing it in the backend means `get_user` refuses as well, so un-approving an account ends its **existing session**, not just its next login — which is what an admin clicking the toggle expects; (b) `createsuperuser` would otherwise produce an account that can't use the site's own login form, so new superusers are auto-approved on creation; (c) **`/admin/login/` remains reachable** with a username, because it authenticates through `ModelBackend`. That is the deliberate recovery path if this locks everyone out, and it is a real gap for `is_staff` accounts — accepted because admin access is already governed by `is_staff` plus model permissions. **Ship prerequisite: 6 of 10 local accounts, both superusers among them, have `is_approved=False`.** Run the 0.3 audit against prod and approve that list first. |
| 1.11 | Tests for every item above | ✅ | **48 new tests, 145 total**, with the CMS's 80 intact: [doctorDashboard/tests.py](../doctorDashboard/tests.py) 16, [appointments/tests.py](../appointments/tests.py) +23, [useraccount/tests.py](../useraccount/tests.py) +9. **Phase gate:** ✅ **met.** An anonymous visitor is refused by every dashboard route, no destructive endpoint responds to any method, and patient PII is unreadable without proving a claim to it — each verified by a test that has been shown to fail when its fix is removed, not by inspection.

## Phase 3 — Notification layer

Design §9.1. Built before the flow, because the flow is unusable without it.

| #   | Task                                             | Status | Notes / Remarks                                                                                                                                                                                                                                                                                 |
| --- | ------------------------------------------------ | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3.1 | `notify(event, appointment, to=...)` event API | ✅ | [appointments/notifications/](../appointments/notifications/). Call sites emit events; nothing outside `channels.py` knows what email is. **One deviation from the design's sketch:** who hears an event is declared on the *event*, not passed at the call site. `to=` still works as an escape hatch, but a call site that has to remember the audience is one that can get it wrong silently — and this is easy to get wrong in exactly the way decision 8 warns about, since a new booking must reach **the doctor being booked** rather than a central AGKI inbox. | 3.3 | `SmsChannel` stub | ✅ | Raises `NotImplementedError`, and the seam is **exercised**, not just declared: a test registers SMS for an event, asserts it queues to `Appointment.phone`, and asserts the send fails loudly and is recorded rather than silently looking like success. **Phase gate:** ✅ **met.** All eight events render, queue, deliver by email through the console backend, and are logged with their content; no module in either app calls the mail API except the email channel (asserted by a test that scans the source). Ten Phase 3 guarantees were mutation-checked.

**Two misses in that check were worth more than the eight hits.** The first showed a test gap — the delivery-mode default was never asserted, so it is now, on the fallback rather than the environment variable. The second exposed a **real bug**: the original claim counted attempts, which stops two runs that read a row simultaneously but *not* a run that starts while another is inside `send()`. That second run saw the row still pending and would have delivered it again — a duplicate email, in exactly the circumstances the queue exists for, since a slow mail host is what makes runs overlap. The claim is now an atomic `PENDING → SENDING` transition, with a stale-claim release for runs that die mid-send, and four tests cover the cases.

### 3.7 Why delivery runs from cron, and what else was considered

You asked about a service worker, a cron job "or something similar". The short answer is cron, and the reasoning is worth writing down because the alternatives fail for different reasons.

| Approach | Verdict |
| --- | --- |
| **Send inline, in the request** | Rejected. It couples two unrelated things: a mail server having a slow afternoon makes booking *feel* broken, and a mail server that is down makes booking *be* broken — for a message that is not part of booking. It also leaves a failed send nowhere to go: no retry, no record, nothing to tell an administrator afterwards. |
| **Service worker** | Not applicable, and worth being precise about: a service worker runs in the **visitor's browser**. It can show a Web Push notification to somebody who has visited the site and granted permission; it cannot send email or SMS, and it does not run when nobody is visiting. It would be a reasonable *addition* later if AGKI wants doctors to get browser alerts on top of email — a separate feature, needing VAPID keys and a push subscription store. |
| **Celery / RQ / a task queue** | Rejected on this host. Both need a broker (Redis, RabbitMQ) and a long-running worker process. Shared cPanel hosting provides neither. |
| **A background thread in the request** | Rejected. Passenger starts and kills application processes as it pleases, so a thread can be killed mid-send with the row still marked pending and nobody the wiser. |
| **Cron + a database outbox** ✅ | What shipped. Cron is the one scheduler this host actually offers, Phase 6 needs it anyway for expiry, and the outbox table was already in the design (§9.1) for auditing — making it the queue as well costs one status column and gives retries, a record of what was said, and a place for an administrator to look. |

**The one failure mode, and it is silent:** with `NOTIFICATIONS_DELIVERY=queued` and no cron entry, messages queue forever and nobody is told anything. Same class of failure as the expiry cron in 6.4, and it needs the same treatment — watch a real run, do not just add the entry. In development the default is `immediate`, so a developer sees messages in the console without running cron.

```
# cPanel → Cron Jobs. Every minute; the command is bounded (--limit) and
# safe to overlap with itself.
* * * * * cd /home/<user>/<app> && /home/<user>/virtualenv/<app>/3.12/bin/python manage.py send_pending_notifications >> /home/<user>/logs/notifications.log 2>&1
```

### 3.8 Services that need a human, not code

Everything below is an account, a credential or a DNS record. None of it can be written here, and the notification layer is finished without it — but **email will not actually arrive in a patient's inbox until the first two rows are done.**

| Service | What it is for | What is needed | Blocking? |
| --- | --- | --- | --- |
| **SMTP mailbox** (cPanel, or the domain's mail host) | Every message the system sends | A real mailbox on `agkimedicallaboratory.co.tz`, and its credentials in `EMAIL_HOST` / `EMAIL_HOST_USER` / `EMAIL_HOST_PASSWORD` / `DEFAULT_FROM_EMAIL`. The settings already read them from the environment and refuse to boot in production if they are missing. | **Yes** — nothing is delivered without it. |
| **SPF + DKIM DNS records** | Stopping the mail going to spam | TXT records for the sending domain, added at the DNS host. Transactional mail from a new sender with no SPF/DKIM is very often filtered — and a booking confirmation in a spam folder is indistinguishable from one that was never sent. | **Yes, in practice.** Mail "sends" without it and still does not arrive. |
| **Cron entry** | Delivering the queue (3.7) and expiry (6.4) | One cPanel cron line, plus watching a real run. | **Yes** in production, where delivery is queued. |
| **Transactional email provider** (SendGrid, Mailgun, Postmark, Amazon SES) | Deliverability and volume, if cPanel SMTP proves rate-limited or unreliable | An account and an API key or SMTP credentials. **No code change** — swapping `EMAIL_HOST` is enough, because nothing outside `EmailChannel` knows how mail is sent. Worth having as the fallback plan rather than a first step. | No |
| **SMS provider** — Africa's Talking, Twilio, or a local aggregator | The SMS channel (3.3), when AGKI wants it | An account, credit, an API key, and — the part that takes longest — a **registered sender ID**. In Tanzania alphanumeric sender IDs are regulated by TCRA and registration goes through the operator; expect this to be measured in days, not minutes. Then `SmsChannel.send()` is implemented and `"sms"` is added to the events that want it. | No — deferred by decision 3 |
| **Video meeting links** (Google Meet, Zoom) | `meeting_url` on online appointments | Nothing technical: the doctor pastes a link when confirming the mode (decision B). Becomes an integration only if AGKI later wants links generated automatically. | No |

**Not needed, deliberately:** no broker (Redis/RabbitMQ), no worker host, no push-notification service. The queue is a database table and the scheduler is cron, both of which this host already has.
